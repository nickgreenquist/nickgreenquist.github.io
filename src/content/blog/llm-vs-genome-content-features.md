*A two-tower recommender experiment on MovieLens 32M comparing LLM-generated movie features to the hand-curated MovieLens tag genome.*

## TL;DR

- MovieLens ships a 'tag genome': a dense matrix of how well each tag describes each movie. It sits on top of fifteen years of community tagging plus a volunteer survey, which no normal company has.
- I built a replacement with an LLM instead. I scraped each movie's public text (TMDB and Wikipedia) and had Claude Sonnet score it on 132 tags taken from the genome. All \~9,375 movies took one day and about \$200 in API calls.
- In a bare-bones two-tower model (interaction history plus one content vector), the LLM features beat a no-content baseline and slightly beat the genome: MRR 0.1155 (LLM) vs 0.1148 (genome) vs 0.1121 (no content).
- Add MovieLens's curated genres, user tags and year back in, and neither content vector helps much anymore.

![Recommendations from the deployed app for a 'pixar animation' genome-tag query](/blog/assets/LLMvsGenome/pixar_movies.jpeg)

*A 'pixar animation' query in the deployed app. The user's taste vector here comes entirely from movie content (the genome tags plus the LLM features from this post), with no user-ID embedding.*

## The problem

A two-tower recommender learns an embedding for every item. For popular items, collaborative signal (who watched what) does most of the work. But it's weakest exactly where you need help: the long tail, and new items nobody has touched yet. That's what a 'content vector' is for. It's a dense description of what the item is, no matter who has watched it.

MovieLens has a really good one, the tag genome: `rel(movie, tag) ∈ [0,1]` for 1,128 tags × 16,376 movies (≈18M scores) in MovieLens 32M. It also isn't hand labeled like most people think. GroupLens collected 50,203 judgments from 676 volunteers (a fraction of a percent of the matrix) and filled in the rest with a regression model. That model's features were mined from a huge existing pile of community tags (186,000 users, 17M ratings, 246,000 tag applications since 1997) plus crawled IMDb reviews. Even then it only covers the well-tagged head: those 16,376 movies are \~19% of MovieLens 32M's 87,585 titles.

A team setting up recommendations for a new catalog has none of that. They usually don't have clean genre labels on every item or a set of user tags either (MovieLens has 306 of those). What they do have is interaction logs (usually implicit, like clicks and watches, not 1–5 star ratings) and each item's public text.

So I wanted to answer two questions:

1. In that bare setting, does a content vector help at all?
2. Is one generated by an LLM good enough to use instead of the genome?

## The setup

Everything is fixed except the content slot: same two-tower architecture, same data, same loss, same 160k-step schedule, same eval. There are three arms:

- A (genome): the 1,128-dim genome scores fill the content tower.
- B (LLM): 132 LLM-extracted dims fill it instead.
- C (no content): no content slot at all. This is the floor.

The main experiment runs these in a 'base' model, written C′ / A′ / B′. The user side is just a single implicit history pool (the sum of the ID embeddings of the items a user touched, no ratings) plus the content slot. No genres, no user tags, no year, no rating-based pools. That's about as close to what a real team has on day one as I could get.

| Arm | User tower | Item tower | Params |
|---|---|---|---|
| **C′** (no content) | `1×sum_pool_id(32) = 32` | `movieId(32) = 32` | 383,840 |
| **A′** (+ genome) | `1×sum_pool_id(32) + genome_ctx(32) = 64` | `genome(32) + movieId(32) = 64` | 472,480 |
| **B′** (+ LLM) | `1×sum_pool_id(32) + llm_ctx(32) = 64` | `llm(32) + movieId(32) = 64` | 408,736 |

Genome's content tower is actually the biggest of the three. A couple of other choices also cut against the LLM:

- The LLM's 132 dims are derived from genome's most discriminative tags, so both feature sets measure the same axes. The LLM gets no credit for anything it could pull from text that genome never tagged. (An LLM could also draft its own taxonomy by clustering recurring themes across plots. I didn't do that, to keep it a fair fight.)
- Genome goes in at 1,128 dims and the LLM at 132, and both get compressed down to 32. That's the one real asymmetry, and if anything it doesn't help the LLM.

Using LLMs to generate item features isn't new (KAR, ONCE/GENRE, LLMRec, RLMRec, and KAR reported a production A/B gain at Huawei). What's different here is the baseline: the LLM goes up against the genome on its own axes, with a no-content floor to measure the lift.

## Generating the features

For each of the \~9,375 movies (9,366 scraped successfully):

1. Scrape: TMDB first (overview, tagline, genres, top-billed cast, director, writers, keywords), then the Wikipedia plot and factual prestige info (Oscar wins/noms, Criterion status, box-office scale).
2. Extract: six structured-output calls to Claude Sonnet (run through Claude Code), one per feature group: themes, tone, setting/era, provenance/structure, reception/prestige, and visual medium. Each group has \~20–30 dims and every call is locked to a JSON schema.

I split it into six calls because a single 130-dim prompt hits 'lost in the middle' and defaults the later dims to 0.5. Structured output matters too, since free-form output silently corrupts the tensor. And the visual and prestige groups are factual only: animated or black-and-white is fine, "visually stunning" guessed from a synopsis is not.

Since every movie is scored on its own, the calls run in parallel, and the whole corpus was scraped and extracted in one day by one person.

These all look right to me. Alien fills every group (and `cgi_heavy` is only 0.3, since it used practical effects). Toy Story gets 1.0 on `animated` and `computer_animation`, and is `feel_good` and `comedic` where Alien is `tense` and `dark`. Before Sunrise (two strangers talking through one night) gets a 1.0 on `romance`, an `intimate` and `reflective` tone, and almost nothing for genre, visual medium or prestige. It even gives `france` a 0.2, just under the cutoff. The extractor reports what's in the text and not much else.

## Results

The eval is a held-out 'rollback' protocol: for each validation user, the context is their history so far and the target is their next watch. That's all 19,134 validation users, n = 382,138 examples (for reference, a random Hit@250 baseline is 2.7%). I also replicated it on a smaller 'Phase 1' corpus of the 4,461 most-rated movies.

| Metric | C′ (pure CF floor) | A′ (+ genome) | B′ (+ LLM) |
|---|---|---|---|
| Hit@5 | 0.1500 | 0.1538 | **0.1555** |
| Hit@10 | 0.2178 | 0.2229 | **0.2236** |
| Hit@50 | 0.4560 | 0.4644 | **0.4647** |
| NDCG@10 | 0.1259 | 0.1290 | **0.1297** |
| **MRR** | 0.1121 | 0.1148 | **0.1155** |

![Content's lift over a pure-CF floor in the universal setting, and how it vanishes once the curated metadata is added back](/blog/assets/LLMvsGenome/fig1_content_lift.png)

*Figure 1. Left: in the base model, both content sources beat the pure-CF floor, and the order C′ < A′ < B′ holds on both corpora. Right: add the curated genres, user tags, year and rating pools back in, and the lift over the floor drops to about zero or below (more on that further down).*

What I take from this:

- Content helps when the model has nothing else to lean on. Genome adds +2.4% MRR over the floor and the LLM adds +3.0%.
- The LLM matches the genome and edges ahead. B′ beats A′ on every metric and on every popularity tier. The margin is small (+0.6% MRR, within single-run noise on any one tier), but it's consistent.
- It replicates. On the 4,461-movie Phase 1 corpus (n = 99,846) the order is the same: C′ 0.1133 < A′ 0.1158 < B′ 0.1165.

One caveat: the lift shows up on the popular head, not the deep tail. Down at the ≥200-rating cutoff every arm is near zero, and there are too few examples to tell them apart. So the real cold-start case (where content should matter most) isn't measured here.

## Why it works

Since both feature sets sit on the same axes, I could correlate them directly: for each of the 132 LLM dims, compute the Pearson r against its mapped genome tag(s) across all 9,375 movies.

Mean r = 0.598 (median 0.608), with 99 of 132 dims at r ≥ 0.5 and none below 0.1. By group, visual (0.70), setting (0.68) and provenance (0.64) agree the most, themes and tone sit at 0.56, and reception is lowest at 0.42.

- Best axes (factual): vampires 0.94, documentary 0.89, animated/anime 0.88, western 0.86, WWII 0.86, time-travel 0.85.
- Worst axes (crowd sentiment): imdb_top_250 0.16, criterion 0.18, palme_dor 0.27.

![Distribution of the 132 per-dimension genome-vs-LLM Pearson correlations](/blog/assets/LLMvsGenome/fig2_agreement_hist.png)

*Figure 2. Agreement between each LLM feature and its genome tag across all 9,375 movies. It's highest on factual axes (genre, era, medium) and lowest on crowd-prestige ones like imdb top 250 and criterion, which you can't read from a synopsis.*

So the LLM reproduces most of genome's signal on anything you can read from text (genre, setting, provenance, medium), which is why B′ keeps up with A′. Where they disagree, it goes both ways:

- Only genome has: crowd prestige ("masterpiece", "imdb top 250"), fine niche sub-genres (genome tags *The Good, the Bad and the Ugly* with "spaghetti western" and "ennio morricone", while the LLM just says "western"), and subjective aesthetics.
- Only the LLM has: plain plot facts that genome buries, like "artificial_intelligence" for *2001*, "based_on_book" for *Die Hard*, and "hitman"/"conspiracy" for *Sicario*.

Genome's extra axes mostly track popularity more than content, so they don't help ranking much. In the base model the LLM's plot facts come out slightly ahead.

## What if you already have curated metadata?

The obvious pushback is that I crippled the model. So I re-ran all three arms in a 'rich' model with MovieLens's genres, 306 user tags, year and the rating-based history pools added back.

The content lift goes away for both sources, and the floor even beats the genome:

| Whole-corpus MRR | C (no content) | A (genome) | B (LLM) |
|---|---|---|---|
| **Rich model** | **0.1174** | 0.1144 | 0.1176 |
| Base model | 0.1121 | 0.1148 | 0.1155 |

That doesn't mean content is useless. Arm C already has genres, tags and year, so genome is mostly a second copy of the same info. What each arm loses when you strip that metadata out is more telling:

| Arm | rich → base (whole-corpus MRR) | Δ |
|---|---|---|
| Floor (C → C′) | 0.1174 → 0.1121 | **−0.0053** |
| LLM (B → B′) | 0.1176 → 0.1155 | **−0.0021** |
| Genome (A → A′) | 0.1144 → 0.1148 | **+0.0004** |

Genome loses nothing, because it can rebuild the genre and tag info by itself (genome tags basically ARE that metadata in another form). The LLM loses a little, since its plot/tone/theme features only partly overlap with it. The floor loses the most. So the LLM features overlap less with cheap metadata, which means more of their signal is their own. (This ordering also replicates on Phase 1.)

In short: if you have a rich metadata stack, an extra content vector is redundant. If you don't (most teams), it's worth +2–3%, and the LLM one is the less redundant of the two.

## Cost and speed

A tiny MRR edge is nice, but the bigger deal for me is that a normal team can actually build the LLM version. Every genome dollar figure below is my own estimate (the genome papers don't publish any):

| Dimension | Genome (GroupLens) | LLM extraction (this repo) |
|---|---|---|
| Human labeling | 50,203 judgments (676 volunteers); **\~\$5k–23k (central \~\$10k)** to buy as crowd labor today *(est)* | **Zero** |
| Binding prerequisite | \~15 years of community tagging (186k users / 17M ratings / 246k tag applications, since 1997) + crawled IMDb reviews; accrues with usage, not buyable quickly | The item's own text, exists day one |
| Specialist engineering | LSI/SVD features + rating-affinity + text-mining + a 6-model regression bake-off; **weeks–months** *(est)* | Scraper + schema derivation + 6 grouped prompts; **a few engineer-days** |
| Direct \$ (this corpus) | \~\$10k survey + tens of \$k labor, *only if you already own that tagging history*; **\~\$85–210k** to hand-curate without it *(est)* | **\~\$0 marginal as run**; **\~\$170–220** if reproduced on the metered API (Sonnet \$3/\$15) |
| Wall-clock to build, full corpus | Accreted over \~15 years of community use | **\~1 day** for all \~9,375 items (independent calls, fanned out in parallel) |
| Time-to-first-vector, new item | Effectively **never** until the crowd tags it | **Sub-hour**, zero-shot from text |
| Maintenance / new domain | Re-survey + re-crawl + re-train; new domain = redo everything | Parallel API calls per item |
| Quality (universal setting) | A′: MRR 0.1148 | B′: 0.1155, **matches, edges ahead**, +2–3% over the floor |

A few notes on that table:

- The LLM side isn't free. The full extraction used \~84% of one week's Sonnet quota on my Claude Max plan, which is ≈\$0 marginal under the subscription and \~\$170–220 on the metered API. That's still roughly 1–3 orders of magnitude cheaper. But the price isn't really what matters: for a company without that tagging history, the genome is simply not an option.
- A brand-new item gets an LLM content vector in under an hour (scrape plus six calls). With the genome it effectively never does, since its input features are all zero until the crowd tags the item.
- A content vector on day one also opens the door to cold-start tricks, like using content nearest neighbors to show a new item to users who already like similar items (cf. DropoutNet, NeurIPS 2017). I didn't build or measure that here. Genome could do it too, but only for items it covers.

## Limitations

- One seed per arm, no confidence intervals. The ordering and the metadata results replicate across both corpora, but I'd read the per-tier A′ vs B′ gaps (≤ 0.0007 MRR) as a tie that happens to always lean the same way.
- All arms train and eval on the 9,375 movies with >200 ratings, where genome has full coverage. The bigger gap is the other \~81% of the catalog, where genome doesn't exist at all (the LLM could score all of it for an estimated \~\$1.6–2k metered). So these numbers probably understate how much more usable the LLM approach is.
- A real cold-start head-to-head isn't possible, since there's no genome for those items to compare against.
- Single LLM (Claude Sonnet). This shows Sonnet-class extraction matches genome, not that any cheap model would.
- Movies are an easy case. Every item has a Wikipedia plot, TMDB cast and reviews. Items with three sentences of description are untested.
- The LLM trails on crowd-sentiment tags (r≈0.16–0.18), mostly because I only scraped Wikipedia and TMDB. Pointing the same pipeline at reviews should pick that up.
- Possible training-data contamination: MovieLens and its genome tags are public and discussed a lot online, so the LLM might be partly reciting genome knowledge instead of reading the synopsis. That would inflate the r≈0.60 agreement. Replicating on a fresh catalog would settle it.
- The base model isn't perfectly implicit. Its history pool has no ratings, but the content arms' user-side pooling still weights each item's content vector by rating. It's a small effect.

## Takeaway

If you're building a recommender with implicit interactions, item text and no curated metadata (which I think is most teams), I'd generate content features with an LLM. They beat collaborative filtering alone and match the genome on the genome's own axes. If you already have a rich metadata stack, an extra content vector doesn't add much either way.

The genome and the LLM features are really the same idea a generation apart. Both turn cheap signals into a dense content matrix per item. GroupLens did it with a 50,000-judgment survey and a regression on top of fifteen years of community data. The LLM does it from each item's own text, in a day, for any item at any company.
